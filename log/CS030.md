# CS030 — the achievement celebration panel

Seven phases: the unlock collector (P1), an eight-emblem authoring lab (P2), pasting that table
into the build (P3), the panel itself at game over (P4), a second call site at level end (P5), a
blocking playtest gate (P6), and this closing phase (P7).

## §0.1 correction — the wave-clear window is not a pause

`archive/PLANNED-FEATURES-CS029.md` §10 previewed CS030 with a specific claim: `Achievements.
onUnlock()` is a single choke point (true), and the 2.5s `waveClearTimer` window is "the natural
place to hang the panel" (false). `archive/PLANNED-FEATURES-CS030.md` §0.1 re-grepped the block before any
code was written and found the second half wrong: for the full 2.5 seconds after debris hits zero,
the ship still flies, Hunters and loose garbage are still live and hunting (CS015 P3 made this
deliberate — wave clear triggers on debris-empty alone, and `nextWave()` clears nothing), saucers
can still be on screen and shooting, and collision/coalescence/the dock all keep running.
`nextWave()` fires inline from inside that same `update()` branch, and the next level begins the
very next frame. There is no pause anywhere in that window — the preview's central premise was
wrong.

Paul chose to build the pause anyway, cost fully visible (FORK-CS030-A = a, both call sites): P5
knowingly inserts a genuine new pause into `update()`'s hottest path, freezing a field that may
still contain live Hunters, rather than reusing a pause that didn't actually exist. The P6 gate
(G7/G8) was built specifically to re-check that call after the fact — "is the resume after a
level-end pause fair, and does the per-level cadence earn the interruption." Both gate answers
came back affirmative (see P6 below), so the cost was judged worth it, but the decision was made
with the true cost in hand, not the preview's mistaken "it's already a pause" framing.

## P1 — the unlock collector

`game.pendingAch` (a flushed bucket, appended to by `onUnlock()`, the single unlock choke point)
and `game.celebration` (`null`, reserved for the panel P4 would build). Per spec §0.4: in a
wave-clear frame `nextWave()` increments `game.wave` *before* `Achievements.evaluate()` runs, so a
Perfect Wave earned clearing wave 7 is banked while `game.wave === 8` — the collector therefore
never records or filters by wave, only flushes whole. Not gated on `game.debugRun` (that guard
belongs to `Achievements.save()`, a persistence point; the collector is UI state and a debug run
must still be testable). Data only — no draw, no input.

## P2 — `tools/emblem-lab.html`

Eight designs, measured rather than assumed (the CS028 P1 precedent — the per-craft small
satellite variant was deleted after measurement showed no silhouette survived at r=13). Six tier
emblems are one family: the same delta mark inside the same r=0.66 circle, the ladder expressed as
how much of that circle exists (120° cradle → 240° → 300° → closed → +4 points → points bound in
an outer facet ring). Two off-family pool marks — an hourglass (weekly) and a stamped plate
(untiered lifetime) — both rectilinear, no ring, no delta. Measurement changed two designs before
shipping: Platinum/Diamond's points were originally straight rays at the diagonals and read as an
X cancelling the ring out, fixed to chevrons with feet welded to the 12-gon's edge; the weekly
hourglass's cap bars sat 1.9px off the body, pulled in to clear at a measured 5.1px gap. Lab only —
the game file untouched, no test.

## P3 — `ACH_EMBLEM` + `drawEmblem()`

The lab's export pasted in verbatim near `TIER_NAMES`/`TIER_COLOR`. `drawEmblem(cx, cy, r, tierIdx,
pool)` resolves `typeof tierIdx === "number"` — never truthiness, since `if (tierIdx)` would
silently misroute every Bronze unlock (tier index 0) to the untiered emblem, and Bronze is the
game's most common unlock. Two new `DEBUG_VARS` rows under a new CELEBRATION header
(`celebrationScrollStep`, `celebrationEmblemSize`). Registry moved 85 → 87, section headers 9 → 10
— measured against the live build, not predicted (the prediction has historically undercounted).
Eighteen older suite files that pin literal or derived registry snapshots were repointed to name
these two new rows explicitly, the same "later phase named, never wildcarded" idiom used since
CS025.

## The B-resolves-to-overlay finding

FORK-CS030-B asked how the panel should sit in front of CS029 P2's game-over screen — a screen
retuned one changeset earlier, with its footer still an open playtest knob. The planning session
found a shipped precedent already doing exactly this shape: `if (game.paused) drawMenu();` at the
tail of `draw()` draws `drawMenu()`'s own opaque `menuPanel()` chrome *after* the gameover block,
on top of it, without that block knowing or caring. Resolving B to "overlay" meant the celebration
panel could reuse that exact pattern — draw after, on top, via its own `menuPanel()`-style backdrop
— which **structurally removed** the risk of retuning CS029 P2's tight layout, rather than merely
mitigating it: nothing about that screen's draw code needed to change at all. P4 asserted this with
a source diff (byte-identity pin against the phase's own parent commit), not just a behavioral
test.

The corollary the planning session flagged at the time: because B resolved to overlay rather than
modal-replace, `game.entry`'s initials-entry slots could already be armed and rendering underneath
the panel on the very first game-over frame. FORK-CS030-C ("panel first") was therefore delivered
through **input priority**, not draw order — the panel's guard sits before `game.entry`'s in both
handlers, so a player physically cannot interact with entry until the panel dismisses, even though
entry's slots might be visible (covered by the panel's near-opaque backdrop) underneath it. That
gap — reads as fine functionally, but a player *could* see entry slots peeking from behind the
panel — is exactly what P6's new gate question G6 went back to test.

## P4 — the panel, at game over

`drawCelebration()` in the same tail slot as `drawMenu()`, outside `drawHUD()` so Capture's **H**
never hides it. Content: `[emblem][name + tier badge] / [desc]` per row, inside a clipped scroll
region reusing the Achievements viewer's exact clip/shared-ceiling/▲▼ idiom, but with the panel's
own `scroll` field on `game.celebration` rather than the menu-scoped `game.menu.scroll`. Both
keyboard and gamepad handlers gated, immediately before their respective `game.entry` blocks.
Fanfare: a single `AudioSys.achievement()` on open (FORK-CS030-F's cheapest default, left open for
the P6 gate to retune). Mutation-checked: deleting the gamepad guard failed 15 assertions, deleting
the keyboard guard 21, perturbing one number inside the gameover draw block tripped the parent
byte-identity pin.

## P5 — level-end integration

Per §0.1: this is a genuinely new pause, built with the cost known. In the `waveClearTimer > 2.5`
branch, after the existing perfect-wave bookkeeping and before `nextWave()`: a non-empty
`game.pendingAch` opens the panel and **returns without calling `nextWave()`** — deferring both
`game.levelBanner` and `VoiceSys.sayLevel()`, which both fire from inside `nextWave()`, until after
dismissal. `dismissCelebration()` gained the one branch that calls `nextWave()` for a level-end
open; the game-over site stamps `resume: null` and does nothing further. `update()`'s early-return
was extended with `|| game.celebration` — deliberately **not** `game.paused`, which would satisfy
`menuActive()` and pull in the whole menu-chrome path this isn't part of. A hazard found during the
phase, not named by the prompt: `killShip()` can flip state to `"dying"` **mid-frame**, and
`update()` runs on to the wave-clear branch in the same frame — dying on the exact crossing frame
could otherwise open a level-end panel whose later dismissal would fire `nextWave()` at game over.
Guarded by requiring `game.state === "playing"` at the open check; pinned with a real mid-frame
death in the test. The freeze was verified two independent ways: nothing moved (ship, particles,
`waveTime`, `gameTime`, lifetime play time) across 90 frames, and zero entity `update()` bodies ran
in that span, with `game.paused`/`menuActive()` staying false throughout, pad Start included.

## P6 — the playtest gate

All ten questions answered. `celebrationScrollStep` and `celebrationEmblemSize` both kept at their
defaults (60px, 32px). The six tier emblems read as one ladder; the two pool emblems read as
distinguishable from that family. Fanfare stays once-on-open. The level-end resume was judged fair,
and the per-level cadence was judged to earn its pause — both a direct affirmative answer to the
cost §0.1 exposed and FORK-CS030-A accepted knowingly. The panel still reads celebratory on a
10+-unlock run, and no issue was observed dismissing without scrolling to the bottom.

**G6 was the one answer that changed shipped behavior.** At game over, "panel first, entry
underneath" — the shape B's overlay resolution produced, where a qualifying run's initials-entry
slots could be visible, inert, behind the panel's backdrop — read as broken rather than fine: Paul
called for entry to be hidden entirely, not merely uninteractive, until the panel dismisses. That
is the one piece of code this closing phase carries out.

## P7 — closing phase (this session)

Applied G6: the gameover draw block's `if (game.entry) { drawEntrySlots(...) } else { ... }`
became `if (game.entry && !game.celebration) { drawEntrySlots(...) } else if (!game.entry) { ... }`
— entry stays armed, but its slots don't render while `game.celebration` is set. The other nine
gate answers needed no code; they confirmed shipped defaults. `test-cs030-p4.js`'s byte-identity
pin against the gameover draw block (which P4 legitimately claimed was untouched, at the time) was
repointed — not weakened — to assert identity against the parent **plus** this one named,
gate-mandated substitution, the same "later phase named" idiom the eighteen P3-repointed files
already used.
