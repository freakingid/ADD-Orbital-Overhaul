# CS031 — Player Profiles

A named-roster persistence layer over the three existing `localStorage` stores, so more than one
player on the same browser gets independent settings, bindings and lifetime achievement progress.
Seven phases: the `Profiles` module and legacy migration (P1), the `activate()` reset-then-load
switch (P2), the name-entry screen (P3), the Choose Profile screen (P4), title integration (P5), a
blocking playtest gate (P6), and this closing phase (P7). This changeset also closes a
five-changeset-old standing item — see the P6/P7 section below.

## P1 — the `Profiles` module, per-profile key routing, legacy migration

`Profiles` sits immediately above `const STORAGE_KEY`, `Profiles.init()` immediately above
`loadSettings()`. The one router, `keyFor(base)`, resolves `"p0"` (`PROFILE_LEGACY`) to the bare
base name and every other profile to a suffixed key (`afd_settings_v1:p3`) — ⛔ **`p0`'s stores ARE
the three pre-CS031 frozen keys**, not a copy: the migration mints a roster entry over an existing
machine's data and copies, moves, or rewrites nothing, pinned byte-for-byte by `test-cs031-p1.js`
§C. `afd_profiles_v1` is the fourth key, CS031's own, additive, not frozen; `localStorage` is never
enumerated anywhere in the build. The `LEGACY_KEY` trap (an ungated build handing a brand-new
profile the machine's existing achievement counters) is closed and measured: 26,000 deliveries
reproduced ungated, zero gated. `FLAG-CS031-a`: the roster carries a monotonic `seq` so a removed
profile's id is never recycled — recycling one would resurrect a deleted player's achievements,
since `remove()` is roster-only and doesn't clear that profile's stores.

## P2 — `Profiles.activate(id)`: reset-then-load, no cross-profile bleed

The runtime switch, in six steps: (1) flush the outgoing profile at the key it still owns; (2)
switch `activeId`/`lastUsed` and persist the roster; (3) reset the live runtime to shipped defaults
(`SETTINGS_DEFAULTS`/`AUDIO_VOL_DEFAULTS`, pristine snapshots taken once at load, same idiom as
`DEFAULT_BINDINGS`) — **write-free**, achieved by factoring `returnToDefaults()` into a save-free
`restoreDefaultBindings()` rather than a suppression flag (a flag left set by a mid-`activate()`
exception would silently disable every later save; the split has no such failure mode); (4)-(5)
load the incoming profile over those defaults via the untouched `loadSettings()`/
`Achievements.init()`; (6) re-point the two live audio shadows neither loader moves on its own — the
four gain nodes and `VOICE_PARAMS` — so the incoming player doesn't inherit the outgoing player's
mix and voice. A full save-site audit (all eleven `saveSettings()` call sites plus `Achievements
.save()`'s four) confirmed nothing can fire mid-switch: `activate()` is synchronous and yields to no
event-loop turn.

## P3 — the `"nameentry"` screen

The build's first text field: a 10×4 grid derived from `SCORES_CHARSET` + DEL/DONE/CANCEL, driven by
both abstract grid navigation (gamepad) and a raw keydown passthrough placed after both prior
claimants (the secret-code window, the debug numeric hook) — pinned on the source, since the
harness's `addEventListener` stub makes ordering unobservable behaviorally. Deliberate consequence:
on this screen WASD is text, not navigation, and `p` is text, not pause; arrows/pad/ENTER/ESC still
work as navigation. Renders and validates only (trim + `PROFILE_NAME_MAX` 12 + case-insensitive
`Profiles.nameTaken`) — creates and renames nothing; the verb lives in the `onCommit(name)` closure
the caller supplies.

## P4 — the Choose Profile screen

Rows are `[...roster, "Add Profile"]`; a profile row carries a left/right **verb column**
(`PROFILE_VERBS = ["SWITCH","RENAME","DELETE"]`, resetting to column 0 on every row move) rather than
a modifier key. Confirm at the default column reproduces the spec's plain text verbatim —
`Profiles.activate(id)` + return to the title menu. Delete asks first through the existing modal
(`index: 1` CANCEL still the default). `blankLegacyStores()` overwrites `p0`'s two frozen keys with
the shipped-default blob through the normal guarded save paths — never a raw `removeItem` — by
round-tripping through `Profiles.activate(PROFILE_LEGACY)` first regardless of whether `p0` was
active; non-legacy profiles' suffixed keys ARE `removeItem`'d on delete. `profileDelete()` always
activates a replacement before removing an active profile, so `activeId` is never left dangling
(closes `FLAG-CS031-b`).

## P5 — title integration

`MENU_TITLE` gains `"Profile"` as row 2 (FORK-H → c: the row IS the name display, `Profile: NAME`,
falling back to `Profile: —` on an empty roster); confirm opens `"profiles"` (title-only,
FORK-I — `MENU_ROOT_PLAY`/`MENU_ROOT_OVER` untouched). `TITLE_MENU_Y`/`TITLE_MENU_STEP` became
DERIVED via `titleMenuLayout(n)` (FORK-G → b), a pure function of `MENU_TITLE.length`: N=5 (live) →
Y 324 / step 33, N=6 (CS032's future row) → Y 324 / step ≈26.4 — centered with 24px clearance from
both boundaries at every N. Boot routing (FORK-E → c): `Profiles.firstBoot`, read once at
`game.menu`'s own construction, sends a genuinely empty install straight to `"profiles"`; a migrated
`p0` or an existing roster boots normally to `"titlemenu"`. `FLAG-CS031-d` closed and widened
mid-phase: `Profiles.activate()` now resets both `game.stats` AND `game.wave` before
`Achievements.init()` — `game.stats` alone still let `untouchable` bleed across a switch, since its
predicate also reads `game.wave` directly, a field `resetGameStats()` never touched.
