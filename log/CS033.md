**CS033 ran off-cycle, directly from chat prompts — there is no
`PLANNED-FEATURES-CS033.md` and no `IMPLEMENTATION-PHASES-CS033.md`, and none
will be written.** Authoring either retroactively would be a record of a plan
this changeset never actually followed; this file is the changeset's record

phase sets it). Judgment calls that would normally be settled by a plan doc

## P1 — `player_id`

A `playerId` field, additive on each `Profiles.roster[i]` entry (no sixth
`localStorage` key — it rides inside the existing `afd_profiles_v1` roster).
`Profiles.ensurePlayerId(id)` (`orbital-overhaul.html:4721`) is the one writer:
mint-if-missing via `crypto.randomUUID()`, no-op otherwise, never regenerated
once set. It's called at exactly two touch points — `Profiles.init()` (this
boot's active profile, `:4819`) and `Profiles.activate(id)` (a switch,
`:4890`) — never at `add()`, so a profile sitting unused in the roster stays
unminted until it's actually activated. A profile created before this field
existed backfills the same lazy way, the first time it's next activated;
`save()`/`load()` treat a missing `playerId` as `undefined` → `null`, the
exact state `ensurePlayerId()` reads as unset (known-value-else-default,
`:4795`–`4798`). `player_id` is never rendered anywhere — `display_name` (the
existing `name` field) stays the sole user-facing identity.

- **Decision — mint timing.** The prompt said "minted once the first time a
  profile is used" without defining "used." `Profiles.init()` /
  `Profiles.activate(id)` were chosen as the two touch points; a roster entry
  that's never activated stays unminted. Verified the backfill is stable
  across reboots (`scratchpad/test-cs033-p1.js`) before Phase 2 started, per
  the explicit ask to confirm this first.

## P2 — `lib/kit-leaderboard.js` integration

Integrated `lib/kit-leaderboard.js` (coinless-kit v0.1.0), a shared client
module maintained outside this repo, against the already-deployed
`scores.coinlessgames.com` Worker.

- `Leaderboard` (`orbital-overhaul.html:8296`, search for `const Leaderboard =
  {`) is the one call surface for `window.KitLeaderboard`. Every entry point
  is safe to call with the module absent; `leaderboardModuleAvailable()`
  (`:8295`) is the guard.
- `beginRun()` fires once per `resetRun()` (`:7330`), harmlessly on a resumed
  run too, since `eligible()` gates the resumed run out at `submit()` instead.
- `submit(outcome)` is called from exactly two real sites: the death seam
  (`Leaderboard.submit("died")`, `:9257`, same seam `HighScores`' own top-10
  check already uses) and `quitToTitle()` (`Leaderboard.submit("quit")`,
  `:4068`, gated `if (game.state === "playing")`, read **before** that
  function overwrites `game.state` — the same function also serves as
  gameover's own "Quit to Title" row, an already-ended run that must not
  submit a second time).
- A "Leaderboard" title-menu board screen (`Leaderboard.openBoard()`, `:4247`;
  left/right cycles the time window, `:4384`–`4385`), a queue-pending
  indicator on the title screen (`Leaderboard.queueLength()`, `:11159`), and
  the `NAME_CHANGE_NOTICE` rename gate (`:5122`, `menuProfiles`'s RENAME
  branch — the one other legitimate direct read of `window.KitLeaderboard`
  besides the module bridge tag itself).
- Loaded via the ES-module bridge at the end of the file (`:11657`–`11664`): a
  second, separate `<script type="module">` tag whose only job is `import *
  as KitLeaderboard from './lib/kit-leaderboard.js'` and assigning it to
  `window.KitLeaderboard` — no game logic in that tag.

- **Decision — ES-module exception to the single-script-block / `file://`
  invariant.** `kit-leaderboard.js` ships as an ES module and was not to be
  forked locally, but ES modules are blocked outright on `file://`. Resolved
  exactly as built above: the core game (classic script, unmodified) still
  opens and plays via `file://` by double-click with zero regression; only the
  leaderboard enhancement is absent there, exactly like any other missing
  optional file. A local dev server is needed only to exercise the
  leaderboard itself. Confirmed with Paul before implementing — this was the
  one blocking item Phase 2 couldn't proceed past. Full contract:
  `EXTERNAL-FILES.md` rule 1/2.
- **Decision — submit eligibility mirrors `HighScores`' existing gate.**
  `!game.debugRun && !game.resumedRun`, the same predicate `HighScores`' top-10
  check already uses at the "dying"→"gameover" seam. Not stated anywhere for
  the leaderboard specifically, but directly implied by the existing
  `game.resumedRun` invariant ("bars… persisting achievement/lifetime
  writes") — posting a resumed or debug run's score to a *public* board would
  be a worse version of the thing that invariant already forbids locally.
- **Decision — `'completed'` outcome has no call site.** The module's outcome
  enum is `'died' | 'completed' | 'quit'`; this game has no win condition
  (waves escalate indefinitely, per `DIFFICULTY-LEVERS.md`). Submitting
  `'died'` and `'quit'` only, rather than inventing a "completed" trigger to
  satisfy the enum. Revisit if a future changeset adds any kind of
  run-completion condition.
- **Decision — `stats` payload limited to two keys at P2: `wave_reached`,
  `canisters_delivered`.** These are the exact names
  `lib/docs/kit-leaderboard-client-api.md` uses in its own worked example for
  `gameId: 'orbital-overhaul'`, which reads as real registry field names
  rather than a generic placeholder. Nothing else about the Worker's
  `statsFields` list for this game is visible from this repo, and the doc
  states a key mismatch only sets a flag server-side, never a rejection — so
  nothing else was guessed to "fill out" the payload at this phase.
- **Decision — `quitToTitle()` reused as-is, gated by a pre-overwrite
  `game.state` read.** That function already serves two different callers (a
  live run's confirmed Quit, and gameover's unconfirmed Quit to Title); rather
  than splitting it, `outcome: 'quit'` is submitted only when `game.state ===
  "playing"` at entry, which is false for the gameover caller. Keeps the
  existing single-function shape intact.

## P3 — per-game saucer counter + extended stats payload

`game.stats.saucerKills` (`:6904`, new counter — saucers of **both** sizes,
distinct from `smallSaucerKills` and from `Achievements.lifetime.saucerKills`,
which is cross-game) increments in `destroySaucer()` (`:7676`) and feeds
`Leaderboard.submit()`'s `stats` object alongside the two P2 keys. A new
`garbage_satellite_kills` key reads from the pre-existing `game.stats.debrisKills`
counter — no new counter needed. `Leaderboard.submit()`'s `stats` payload
(`:8343`–`8347`) is now four keys:

```
stats: {
  wave_reached: game.wave,
  canisters_delivered: game.stats.delivered,
  saucer_kills: game.stats.saucerKills,
  garbage_satellite_kills: game.stats.debrisKills,
}
```

Also narrowed CS024 P1's `destroySaucer` byte-pin (`test-cs024-p1.js` TRAP 2)
to exclude this phase's one new line, per that same TRAP's own "narrowed,
stated positively" precedent — confirmed with Paul before touching an
out-of-scope test file.

- **Decision — the two new stats keys are unconfirmed guesses, unlike P2's
  two.** `saucer_kills` and `garbage_satellite_kills` are not sourced from the
  module's worked example — the Worker's real `statsFields` registry for this
  game isn't readable from this repo, so both are best guesses at what a
  human-readable field name would be. Per the module doc, an unrecognized key
  only sets a flag server-side and never rejects the submission, so a wrong
  guess here is cosmetic, not breaking. If the real names ever surface, the
  fix is a rename at the single `Leaderboard.submit()` call site.
  `durationS` was deliberately **not** duplicated into `stats` — it's already
  a top-level field on every board entry per the module's own contract.
  Hunter kills were explicitly declined: no per-game counter exists for
  player-only Hunter-core kills distinct from `Achievements.lifetime`, and
  none was added to serve this.
