## ⛔ §1 is NOT a bug fix for CS035 P3. Read this before reading anything else.

A future reader will otherwise conclude the earlier phase was broken. It was not.

CS035's gate reported the level-end window as apparently inert (G9), and G9–G14 went unanswered as a
result. **The window ran.** What it did not do was *announce itself*: `PLANNED-FEATURES-CS035.md`
§3.1's FORK-L resolved to "the player retains full control throughout — thrust, rotate, fire, tow,
dock. Steps 2/4/5 are ordinary gameplay frames with damage switched off." So the field kept
simulating, Hunter Satellites kept hunting, and the only tell was a 2 Hz alpha pulse on the ship.
**CS035 P3 shipped exactly what its own spec asked for.** CS036 asks for a *different thing at the
same seam* — a ceremonial pause: the action stops, "Level N Complete" holds until the player presses
on, the Achievements panel runs if there is one, "Level N+1" announces as it already did, play
resumes. Two specs, one seam, no defect between them.

⛔ **Half the desired sequence already shipped** and was not touched: the Achievements panel already
deferred `nextWave()` to `dismissCelebration()` (CS030 P5), and `nextWave()` is what seeds
`game.levelBanner` and fires `VoiceSys.sayLevel()`. Panel → "Level N+1" → next level was already the
shipped order, and the `return` that *is* that deferral is a standing invariant. CS036 built only the
front half: freezing the field at wave-clear rather than at panel-open, and an announcement during
that freeze.

## P1 — The level-end freeze primitive, built and proved INERT

New `game.levelEndFreeze`, declared in the game literal and reset in `resetRun()` only — deliberately
not `nextWave()`, which runs *inside* the freeze; added to that function's standing ⛔ note beside the
other three in-flight fields.

New `updateLevelEndFreeze(dt)`, a **reduced sim** on the shipped `updateDeath()` model, branching
**before** `update()`'s general early-return rather than adding a term to it. Spec §0.3's table is the
reason: four things live below that return, and a naive extra term stalls all of them. This branch
runs `AudioSys.thrust(false)` (both existing early-return paths do, or a player thrusting on the
killing frame gets a stuck engine loop over a motionless field), the level-banner tick, and
`VoiceSys.update()` — and deliberately **not** `Achievements.evaluate()` or the heartbeat, because the
celebration panel's own freeze already stops both and the wave-clear `return`'s comment says why in
terms. `updateToasts(dt)`/`updateMusic()` live in `loop()`, never in `update()`, and needed no work.

The banner tick moved verbatim into a new `tickLevelBanner(dt)`, called from both paths from one
function and never twice — ⛔ **without it the freeze is a hard hang**, since the unfreeze P3 later
built is a read on `game.levelBanner.life`.

Nothing set the flag; P2 armed it. Registry unmoved at 106. New `scratchpad/test-cs036-p1.js` (52
assertions, seeded) drives the real `update()` with the flag set by hand: Hunter, Garbage Satellite,
saucer, bullet and loose Debris all byte-identical across 120 frozen frames; the ship neither moves,
rotates, recharges nor fires with rotate/thrust/fire held; a stretched chain does not settle a pixel;
a Hunter on the hull deals and takes no damage; `levelBanner.life` ticks exactly one `dt` per frame in
**both** paths and reaches 0; a parked critical voice line still drains; `Achievements.evaluate()` and
the heartbeat run **zero** times — each paired with an unfrozen frame doing the opposite. **Eight
mutations** (branch deleted, each of the three calls dropped, the two stops re-added, a double-tick,
`nextWave()` clearing the flag, `resetRun()` forgetting it) were confirmed to fail it.

## P4 — The Hunter heartbeat punch (spec §2)

**No new mechanism.** CS035 P4's asymmetric grow/shrink/clamp/flip is unchanged, `this.radius` /
`this.shape` / `this.inner` untouched, `LEVERS` stays 18, the pulse stays draw-only on a fresh vertex
array per frame. Four `def`s retuned toward a harder punch and a slower settle: envelope
`hunterPulseMin`/`Max` 87/125 → **80/150** (38 → 70 points), `hunterPulseGrow` 55 → **900 %/s**,
`hunterPulseShrink` 28 → **20 %/s**. New cycle: ~0.08 s out, ~3.5 s back, ~3.58 s a beat (was
~2.05 s).

`hunterPulseGrow`'s **`max` bound** — the binding constraint spec §2 named — was raised 300 →
**5000 %/s**, chosen so the raised bound sweeps the new envelope in under one 60 fps frame
(70/5000 = 0.014 s < 1/60 s): genuinely instantaneous, not merely faster. `hunterPulseMax`'s own bound
(200) and `hunterVolatileAge` (60) are untouched — nothing in the retune argued for moving either.

⛔ **G18's colour ask stays reversed** — `COLOR.satellite` unchanged, `lerpColor()` stays deleted; the
punch is motion-only, per Paul's explicit re-decision at the CS036 planning session.

New `scratchpad/test-cs036-p4.js` (52 assertions): the raised bound and all four retuned defs read
from the registry; CS035 P4's don't-mutate (§G) and radius-unmoved (§F) invariants re-run against the
faster grow; `pulseScale` non-vacuously reaches and reverses at both envelope ends; the legs measured
by the frame `pulseUp` flips (not by epsilon-comparing to a target, which drifts against the clamp's
float arithmetic) — grow ≤ 6 frames, shrink ≥ 30× longer. **Four mutations** confirmed to fail it.

### ⛔ FLAG-CS036-a — H10/H11 were almost certainly measured against STALE PERSISTED KNOB VALUES

H10's report is arithmetically inconsistent with what P4 shipped, and the discrepancy has a measured
mechanical explanation that is worth more than the gate answer itself.

`saveSettings()` writes `debug: { ...debugShown }` — a **full snapshot of every knob**, not just
edited ones (`debugShown` is seeded for all 106 entries at boot by `resetAllDebug()`). `loadSettings()`
then re-applies every finite in-`[min,max]` stored value over the registry default via `applyDebug`,
and `debugOverride` defaults ON. **Consequence: for any installation that has ever saved settings — a
volume change, a rebind, a profile switch — a later `def` retune does not reach the player at all.**
The stored value wins.

All four CS035-era pulse values sit inside CS036's new bounds, so all four survive the retune and are
re-applied. Measured through the harness with a seeded store:

| | envelope | grow leg | shrink leg | beat | grow as % of shrink |
|---|---|---|---|---|---|
| fresh boot (what P4 shipped) | 80–150 (70 pts) | 0.078 s | 3.500 s | 3.58 s | **2.2 %** |
| stale reload (CS035 gate values) | 87–125 (38 pts) | 0.691 s | 1.357 s | 2.05 s | **50.9 %** |

Paul asked for the grow leg to take "like 20 % of the time it takes to shrink from large to small."
**The shipped defaults already exceed that by ~9×.** The stale reload, at 50.9 %, is a near-symmetric
oscillation — which is precisely what H10 describes ("it just seems like it pulses in and out at a
regular rate"). H13 corroborates from the other side: `dockPingCooldown` is a **new** id with no
stored value, its `def` applied normally, and that answer came back **yes**.

**Nothing was retuned in response.** Two reasons, both decisive: the ask is already met nine times
over, and — more importantly — moving the `def`s again *cannot* change what Paul sees while the stored
values are what his build reads. The fix is diagnostic, not numeric.

⛔ **Before the next gate:** in the debug panel, either set **"Overrides Applied" → OFF** (which makes
every row read its registry `def` without discarding the edits) or use **"Reset all debug knobs to
defaults"**. Then re-ask H10/H11. This applies to the whole gate, not only the heartbeat — H6's
`levelEndFade`/`levelEndGracePulseEnd` are subject to the identical mechanism.

Whether the full-snapshot save is *itself* wrong is a design call and was not taken here. It is the
known-value-else-default rule working exactly as specified; what is new is the observation that it
makes `def` retunes invisible to every existing installation, which the gate protocol depends on.

## Carried-forward known issues (not resolved this changeset)

- **⛔ FLAG-CS036-a** — a `def` retune does not reach any installation that has ever saved settings.
  See the P7 section above. Diagnostic, not fixed.
- **A wave that spawns ZERO Garbage Satellites now soft-locks the level (P2).** Unreachable in shipped
  play (`junkCount` floors at 3), reachable from the debug panel, whose `junkCountFloor`/`Ceil` both go
  to 0: the field is empty on the next frame and the `waveClearTimer === 0` latch cannot re-arm, so no
  further ceremony fires. The pre-CS036 build advanced a wave every `levelEndHold` seconds instead —
  equally degenerate, differently. Narrowing the arm is a design call the spec does not cover.
- **The two announcements can overprint (P3, cosmetic, debug-knobs-only).** A still-live "Level N"
  banner and "Level N Complete" draw at the same `levelBannerY`/`levelBannerSize`. Reachable only by
  raising `levelBannerTime` far enough that a wave clears under a live banner.
- **CS035's banner-crossing edge, re-derived (P3) — the symptom is GONE; a knob inequality is what is
  left.** Measured in four staged scenarios. *The old banner expires during the hold:* the one-shot
  still arms the grace early, but `levelEndGraceT` only counts down in `update()`'s playing body, which
  the freeze replaces — so it is parked at full for the rest of the hold and the whole tail, then ticks
  for exactly `levelBannerFade` seconds before that crossing **re-arms it to full** (measured: armed
  t = 0.98, still 3.000 at the unfreeze t = 11.53, re-armed 3.000 at t = 12.03, closed t = 15.05 —
  exactly `levelEndGrace` after the new banner expired). **Nothing is lost.** *The player confirms
  first:* `nextWave()` reassigns `game.levelBanner` wholesale; it cannot occur. *The residue,
  `levelEndGrace <= levelBannerFade`:* only then can the parked grace run out inside the fade window,
  and the re-arming crossing is refused because the one-shot reads `levelEndSafe`, now false. Shipped
  is 3.0 vs 0.5, a 6× margin.
- **⛔ Two MORE moving-`HEAD` pins survive in `test-cs023-p3.js`, passing VACUOUSLY (P6).** `headSrc()`
  still feeds the `debrisBounce` line count (~599) and the byte-strict `shieldDeflect`/`shieldBounce`
  compare (~641); on a clean tree both compare the file to itself and cannot fail. TRAP 3 surfaced only
  because it carried a "not a vacuous pass" guard; these have none. Each needs a SHA chosen and the
