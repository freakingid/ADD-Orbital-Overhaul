## P2 — Vocabulary glossary and doc sweep

Added `CLAUDE.md`'s **Vocabulary** section: the four canonical terms (Garbage Satellite, Debris,
Hunter Satellite, Recycle dock) plus the code-inversion map. **The build's names for two of the four
are inverted** — what the code calls `DebrisSatellite`/`game.debris` is canonically the Garbage
Satellite (shoot it, it splits); what the code calls `Garbage`/`game.garbage` is canonically Debris
(tow it to the dock). **Code identifiers were deliberately NOT renamed** — the inversion is ~278
sites of load-bearing history, not a defect, and renaming it would be pure churn for zero behavioural
gain. Achievement `id` values are exempt from any sweep on the same principle already governing them:
they're save data, keyed inside `afd_achievements_v2`, and renaming one silently drops that
achievement's unlock for every existing player. The `coinless-kit` Worker's `debris_destroyed` stats
key is old vocabulary under this same table (it counts Garbage Satellite kills) and is frozen in
already-submitted rows — see P4/§0.1 below and the "Corrections" section for how that surfaced.

Prose swept to canonical terms in `ORBITAL-OVERHAUL-GDD.md`, `DIFFICULTY-LEVERS.md`, `RATIONALE.md`.
Player-facing strings: 3 achievement descriptions reworded (`satellite_buster`, `field_sweeper`,
`waste_not`), every "canister(s)" description reworded to "Debris" (count preserved), 4 `DEBUG_VARS`
labels reworded. One spec'd label reverted: `debrisBounceRestitution`'s spec'd "Garbage Satellite
bounce restitution" (36 chars) overflows the debug panel's hard 32-char no-wrap/no-truncate column
budget (`test-cs024-p6c.js` §G) — left as the shipped "Satellite bounce restitution" rather than
widening the column, a layout change out of a strings-only phase's scope (FLAG-CS034-e, resolved at
this closing phase's Gate B — see below). Achievement ids confirmed byte-identical to parent.

## P3 — Hunter Debris yield halved

`HUNTER_GARBAGE` changed from `{3:2, 2:1, 1:1}`-shape (the exact prior table isn't repeated here —
see `git show` on the const) to `{3:0, 2:0, 1:1}`: large/medium Hunter Satellites now emit **no**
Debris on death (still 3-way split; the large tier's core powerup drop is untouched), the small
tier's one low-mass piece is unchanged since that tier spawns no children. A full 13-body lineage now
yields 9 pieces, down from 18.

**This partially reverses v3.3 P4's own reversal** — v3.3 P4 had *increased* Hunter Debris yield
(read `log/CS033.md`/pre-CS033 history for that direction), and CS034 P3 now cuts large/medium back
to zero, deliberately narrower than a full revert: the small tier keeps its one piece. The reasoning
recorded at the time was a Gate A/playtest-driven correction — the surrounding "Balance notes" in the
working `STATUS.md` flagged the risk that late-wave `largeHunterCap`-driven multi-lineage kills could
thin delivery-combo achievements (`heavy_hauler` at 12, `max_haul` at `CARGO_CAP_MAX` 24) more than
intended, a risk left unresolved rather than pre-emptively compensated. **Gate B (B5, this closing
phase) confirms the new yield "feels right"** at a playtest reaching wave 12, with 8/12/24 delivery
combos still reachable there — see below.

## P4 — leaderboard stat key fix + Duration column

`Leaderboard.submit()`'s `stats` key `garbage_satellite_kills` renamed to `debris_destroyed`. **That
key was never registered in the Worker's `statsFields`** — confirmed readable from `coinless-kit`
this phase, correcting `CLAUDE.md`'s prior claim that the registry "is not visible from this repo."
**Every score posted since CS033 P3 (when the key was introduced) through this fix has been showing
flagged (⚑) on the public leaderboard** — the bug was live for the whole of CS033 P3 through CS034
P3, i.e. every public submission across that span. The fix only changes what *future* submissions
send; nothing client-side can retroactively unflag an already-submitted row (a `coinless-kit` data
question, not a game one — §7.1 of the planning doc). Value source unchanged
(`game.stats.debrisKills`, i.e. Garbage Satellite kills under the inverted vocabulary — see P2).
`hunter_kills` stays deliberately unsent: no per-game, player-only Hunter-kill counter exists
(`hunterLineageKills` resets per lineage, `Achievements.lifetime.hunterKills` is cross-game), and none
was added to serve this.

Added `fmtDuration()` (`h:mm:ss` at/above an hour, else `m:ss`, `"-"` on bad input), reused by P7's
browsable High Scores screen. `drawLeaderboard()` gained a `TIME` column between LEVEL and DELIVERED
reading `e.durationS`.

## P6 — achievement reset (FLAG-CS034-a)

New `resetAchievements(pool)`: clear + persist for the **active profile only** ("lifetime" zeroes
every counter and empties `lifetimeUnlocked`/`lifetimeTiers`; "weekly" empties `weeklyUnlocked`; then
`Achievements.save()` — never `init()`, which would reload what was just cleared). Reached from the
Achievements viewer behind two stages: a shared modal (naming pool + profile) then a typed `reset`.
**`menuAchievements()`'s `confirm` is split off from `back`, so ENTER now resets the shown tab instead
of leaving** — the screen has no row cursor (up/down is a continuous scroll), so rather than invent
one, `confirm` became the reset verb. `ACH_HINT` rewritten in the same edit.

**Gate B (B10/B11/B12, this closing phase) confirms this is acceptable** — ENTER-resets is fine as
shipped, the two-stage confirm (modal, then typed word) reads as "right" (neither too heavy nor too
light), and the gamepad path was tested and works. FLAG-CS034-a itself is resolved by that answer,
though its documented consequence (leaving the typed field always returns to the Weekly tab per the
standing CS016 P5 rule, so resetting Lifetime lands you somewhere that shows no visible change) was
not asked about directly this gate and stays open if it ever surfaces as a "did that work?" report —
the fix would be a return-to-tab argument, a design call, not a bug.

## P7 — local high scores reworked; the initials-entry deletion; the RunResult seam

**The 3-slot initials entry is deleted outright**: `game.entry` (both declaration sites), its
dispatcher/commit/renderer, both input handlers' blocks, and all seven guards that referenced it. A
qualifying run's record is now written directly at the "dying"→"gameover" seam, named from
`Profiles.nameOf(activeId)` — no player input required, no 3-character truncation. `SCORES_CHARSET`
is kept (`NAME_CELLS` still derives from it) even though nothing types through it anymore; its
comment was repointed rather than the constant deleted, since deleting it would have meant hand-
deriving `NAME_CELLS` some other way for no behavioural gain.

**The `makeRunResult()` / RunResult seam**: a finished run's numbers — `name`, `score`, `wave`,
`delivered`, `durationS`, `saucerKills`, `satelliteKills`, `build`, `profileId`, `profileName` — are
now read into ONE plain object, once, at the death/quit seam, and handed to BOTH `HighScores.add()`
and `Leaderboard.submit()`. Before this phase those two sites each reached into `game.stats`
independently and could silently drift apart; now there is a single read, and the object survives
being handed across the `KitLeaderboard` module boundary unchanged (every field is a plain value) —
the seam a future `kit-scores` extraction would cut along. `satelliteKills` is the one canonical
CS034 identifier this codebase introduces: the counter it reads (`game.stats.debrisKills`) counts
Garbage Satellites under the inverted build vocabulary (P2); the new *field* takes the canonical
name because nothing persisted used it yet, while the runtime *counter* keeps its own inverted name.
Not a typo, and not a rename to propagate elsewhere.

Records are additive: new ones carry `name` + `durationS`/`saucerKills`/`satelliteKills` and no
`initials`; `HighScores.load()`'s filter dropped its `initials` clause so legacy and new rows both
survive untouched. `HighScores` itself now reads **no game global** — `add(record)` takes a complete
plain object and stamps only `v`/`id`/`ts`.

`SCORES_MAX` 10 → 25; the browsable screen gained an ALL PROFILES / THIS PROFILE toggle over the
still-shared table, its own eight-column renderer at `HS_TABLE_SCALE` **1.4** (FLAG-CS034-b — 1.8
doesn't fit 1000px at eight columns), and scroll clamped by a measured `scoresMaxScroll()`.
`resetHighScores()` moved behind P6's two-stage confirm, reached from the screen's ENTER (same
ENTER-no-longer-returns shape FLAG-CS034-a introduced one phase earlier) and the unchanged debug row.

**Gate B resolves both open flags this phase created**, plus the readability/depth/column questions:
- **FLAG-CS034-b (B13/B14/B15/B16)**: 1.4 scale reads fine ("yes" to readable), all eight columns are
  worth keeping (none to drop), the ALL/THIS PROFILE toggle reads clearly, and 25 rows is the right
  depth.
- **B17/B18**: the TIME column's `h:mm:ss`/`m:ss` format is right, and a real posted score confirmed
  the ⚑ flag is gone on the new row — the P4 fix holds in practice, not just in the client code.

## P9 — closing phase

### Gate B fold-in

Gate B's B1 (readability, 3/5) and B2 named a real problem GATE A's numeric tuning hadn't touched:
Paul's answer wasn't one of the offered size/hold/fade/growth categories, but two concrete
complaints — (a) the ticker's *origin* should be the ship, not the dock, and (b) the incidental
(non-chain) delivery floater is "too dim and hardly readable at all" and should match the towed
ticker's brightness and fade.

**(a) was not implemented.** The code at `orbital-overhaul.html:655-668` documents that CS026 P6
already tried a ship-relative delivery-floater origin, and CS029 explicitly reverted it: "the ship
moves every frame, so a ship-relative origin smears the delivery column as the ship drifts DURING a
visit" — re-confirmed at CS034's own GATE A one phase earlier. Asked directly (this session), Paul
chose to keep the dock anchor and defer the ship-anchor idea to a future changeset with its own real
gate/playtest — the same process CS029 used the first time this exact question came up — rather than
have this closing phase silently re-attempt a design already tried and measured as worse. Recorded
under "Next up" below, not built.

**(b) was implemented**: the incidental floater's colour changed from `COLOR.dim` (`#3a5a80`, a dark
desaturated blue) to `COLOR.dock` (`#70ffa0`, bright green) — the same colour the towed ticker
already uses. Fade/hold were already shared via the live `DEBUG.deliveryFloatHold`/`Fade` knobs (P8),
so brightness was the only real gap. Size (12, versus the ticker's grown 18–36) stays the one thing
distinguishing an incidental delivery from a real haul — Paul's answer named brightness and fade
only, not size, and CLAUDE.md's `POWERUP_DROP_TYPES`-style "don't conflate two different questions"
caution applied here too: dimness (visibility) and smallness (identity) are different signals, and
only the first was reported broken. Five pre-existing suite files carried a stale
`COLOR.dim`/incidental-color assertion and were updated in the same commit:
`test-cs020-p1.js`, `test-cs026-p4.js` (two separate assertions — the source-regex pin and the
runtime push-filter/differs-from-towed check, the latter flipped from "does NOT share the towed
branch's colour" to "DOES share it"), `test-cs026-p6.js`, `test-cs029-p4.js`. A new
`test-cs034-p9.js` pins the live behaviour directly against the real offload block: `COLOR.dock`,
size 12, still dock-anchored, `GAME_VERSION` "1.0.0.34".

B3 (does per-piece growth read as "the chain is paying"?) — yes, no change. B4 (milestone floater
overlap at shipped values: "overlapping (fine)") — no change; Paul explicitly accepts the touching/
overlapping layout GATE A9 measured as clear-but-close. B5–B7 (Hunter Debris yield feels right at
wave 12; combos still reachable) — no change, P3's reversal confirmed correct as shipped. B8/B9
(celebration header reads clearly, sub-line wording ok) — no change; the "abrupt stop of all action"
