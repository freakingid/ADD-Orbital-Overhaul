## P1 — Damage source tagging

`damageShip()` gained a source-tag parameter covering ten categories: Garbage Satellite × sizes
3/2/1, Hunter Satellite × sizes 3/2/1, UFO-large body, UFO-small body, UFO-large shot, UFO-small
shot. The merged hazard loop (`[...game.debris, ...game.hunters]`) discriminates in place via the
`h instanceof HunterSatellite` test already present for Close Shave, plus `h.size` — no new field on
either entity class. Hostile `Bullet` gained a `small` field, set only at its one spawn site inside
`Saucer.update()`; the player's spawn site is untouched. Ten flat `game.stats.dmgFrom*`
accumulators, populated on the non-lethal branch only, mirroring `dmgThisWave`'s own placement — no
gameplay behaviour changed: knockback, i-frames, scoop decay, `dmgThisWave`, `hitsSurvived`,
`everBelowHalf` and the CS023 P3 mutual-kill arms are all byte-identical in effect. No registry rows.

## P2 — The in-game benchmark instrument

A thirteen-run battery over twelve isolated populations (Debris singles/clumps, Garbage Satellites
3/2/1, Hunters 3/2/1, UFOs, particles, floaters, the tow chain) plus one mixed late-wave run, ramping
by `benchRampStep` to `benchMaxCount` and reporting the count at which p95 crosses 16.7 ms and then
33.3 ms — update and draw timed separately; a population reaching the ceiling reports "not reached."
Results export as CSV via `navigator.clipboard`, falling back to the `dumpDifficultyLog` Blob
download. Sealed: five one-line `Bench.running` guards at `addScore`/`saveSettings`/
`HighScores.save`/`Achievements.save`/`Achievements.evaluate`, and `loop()` skips `update()`/`draw()`
entirely. **FORK-CS037-D → (a):** `debugOverride` is forced OFF for the run and restored
unconditionally on completion, ESC abort, and the per-frame `catch` — this is what neutralizes
FLAG-CS036-a (a full-snapshot settings save silently overriding registry defaults) for the
measurement's own duration. New BENCHMARK section, registry 106 → 110, headers 10 → 11.

## P2.1 — Gate A instrumentation

Additive only, over shipped P2 code — no rework of the battery, no existing CSV column altered, no
new registry rows. `PEAK_POPS` + `PlayPeaks` add a passive real-play high-water-mark recorder over
the same twelve populations, sampled once per frame in `update()`'s cleanup block **after** the dead
filters, gated on `Bench.running` (P2's seal, verified to hold in the other direction). Two figures
per population — peak this run, peak this session — the latter module-level with no reset (CS016
P3's precedent for session-scoped, non-`game` state). `benchPredictMixed()` answers Gate A's
predicted-vs-actual question in-build: a linear per-entity extrapolation from each isolated
population's own crossing row, weighted by `BENCH_MIX`, reported as "unavailable" if any weighted
population never crossed. CSV header gained `BENCH_MIX` weights, an environment stamp
(`navigator.userAgent`/viewport/`devicePixelRatio`), and a third table (peak-this-run /
peak-this-session per population).

## ✅ GATE A — Measurement gate, closed 2026-08-19: every population cleared

Run at a 2000-entity ceiling on Edge (Skia Ganesh, AMD integrated) and Chrome (Skia Graphite, RTX
3060 Laptop): **every population reported "not reached" at both 16.7 ms and 33.3 ms, on both
browsers.** The one apparent Chrome crossing (Garbage Satellite lg at 1700) was noise — raw steps ran
9.4 → 17.1 → 16.0 → 11.3 → 11.8, non-monotonic and settling back below the line. Against P2.1's
real-play peaks, the smallest margin was **>12×** (particles: 166 real peak vs. 2000 costing 1.0 ms),
most exceeded 75×, and every figure is a lower bound since nothing crossed. **No population needs a
cap. P3 (static caps) is dropped.**

Secondary findings, carried forward as known issues rather than acted on: draw dominates update cost
by an order of magnitude at 2000 entities (the suspicion that Hunter homing's wrap-aware per-frame
math was the cost centre is refuted), and the late-wave frame hiccup Gate A originally set out to
explain is **not** caused by entity accumulation — its cause remains open, and a future investigation
should start with the fixed per-frame overhead the benchmark deliberately excludes (starfield, ship,
HUD, chrome). Rasterizer backend outweighed GPU (Edge on Ganesh beat Chrome on Graphite despite the
discrete GPU) — any future perf work should size against the slowest representative backend.

## P4 — Periodic gameplay telemetry

`Telemetry` (module-level, the `DebugPanel`/`PlayPeaks` precedent) buffers one row every
`telemetryInterval` seconds of **game time** (new GLOBAL knob, `def` 15; registry 110 → 111).
`Telemetry.tick(dt)` sits beside `PlayPeaks.sample()` in `update()`'s cleanup block, so pause, menu
and level-ceremony seconds cannot reach it. Thirty columns (`TELEMETRY_FIELDS`): score, level, hull,
speed, six remaining-use columns (five `powerBudget` keys + `scoopLevel` — health has none, C10),
seven pickup counts, P1's ten `dmgFrom*` accumulators, `debugRun`/`resumedRun`, and
`game.stats.gameTime`. 400-row ring, oldest off; cleared by `Telemetry.reset()` in `resetRun()`, so
both `startGame()` and `resumeFromSave()` inherit it. Six new flat `*Picked` counters on
`resetGameStats()`, one increment site above `applyPowerup()`'s scoop early-return — health reuses
`healthPicked` rather than adding a seventh, parallel counter. New key `afd_telemetry_v1`, written
each snapshot on the `SaveSlots` idiom (`Profiles.keyFor()`, `storageOK()`, try/catch, versioned
envelope, known-value-else-default), silent on failure — a background write, not a player-initiated
save. No existing key touched. Export is a "Copy telemetry log" debug-panel action row, reachable at
game-over via a new paused-gameover arm on the secret code's gate.

## P5 — Full tow release on damage; "Payload lost." as its own event

Any real HP-dealing hit now calls `scatterChain()` unchanged, hooked on `damageShip()`'s non-lethal
branch below the `s.hp <= 0` exit (`killShip()` already scatters, so the shared return would
double-scatter). Shielded/i-framed/auto-shield hits return false, deal 0 HP, and keep the cargo.
**FORK-B1 → no** (`powerBudget.guard` neither read nor spent; `breakChain()` is not on this path) and
**FORK-B2 → no** (`cargoDamageEvents` untouched — reusing `scatterChain()` verbatim gives both for
free). The release is guarded on a non-empty chain, so a hit taken empty-handed is a genuine no-op
and cannot zero a dock visit's `deliveryCount` through `scatterChain()`'s own side effects.

"Payload lost." moved out of `chain_broken` into a new `chain_lost` event, text and phon verbatim —
no new phon, no `voice-robot-lab` gate. One selection rule at every chain-loss site ("was the chain
non-empty, and is it now empty"): the damage release speaks it, `breakChain(0)` speaks it,
`breakChain(i > 0)` keeps `chain_broken`, the guarded absorb is unchanged, and ship death stays
silent because the `say()` call sits at `damageShip()`'s call site, never inside `scatterChain()`.
`VOICE_PRIORITY` 2 (matching `chain_broken`, strictly below `health_low`'s 3), `VOICE_CRITICAL` true,
`VOICE_QUEUE_MAX` 4 → 5, `VOICE_STILL_TRUE` predicate `game.chain.length === 0`. No registry rows.

## P6 — Resume achievement baseline, both pools

Root cause: `resumeFromSave()` copies `game.stats` out of the slot, and the very next `evaluate()`
finds a batch of achievements — 16 weekly, plus two LIFETIME ones that also read per-game stats
(`untouchable`, `max_haul`) — satisfied on the same frame. `deriveLifetime()`, the silent catch-up
that exists to prevent exactly this, runs once from `load()` and is never re-run at resume — and the
two lifetime ids leak into `afd_achievements_v2` via the **next non-resumed run** in the same
session, a live data-integrity bug, not a hypothetical one.

`Achievements.snapshotResumeBaseline()`, module state (not a `game.*` field), snapshots every active
achievement's `cur()` **blanket over both pools** as `resumeFromSave()`'s new step 3, between the
stats overwrite (step 2) and `nextWave()` (step 5) — earlier snapshots zeroes and fixes nothing;
later, `nextWave()` has already advanced `game.wave`, which `untouchable`'s `cur()` reads. It marks
nothing unlocked; `evaluate()` reads it as a floor (a non-tiered check returns before its `set.add`;
a tiered loop's start index is raised so a baselined tier is skipped, not recorded). It never touches
`weeklyUnlocked`/`lifetimeUnlocked`/`lifetimeTiers`, and is cleared in `resetRun()`.

**FORK-A → (b), FORK-A.1 → (b2):** a post-baseline unlock is genuinely earned and now persists,
through `Achievements.mergeUnlock()` — a second, narrow writer of `afd_achievements_v2`: a targeted
read-modify-write of unlock ids and tier indices only, stored `lifetime` counters returned
byte-identical, guarded `!game.resumedRun || game.debugRun` plus the `Bench.running` seal. (b1), the
simpler "lift the choke point" shape, was refused — it would let a player bank `++` lifetime counters
by reloading one save slot repeatedly, reopening exactly what CS032 P2's resumed-run bar exists to
close. `save()` stays byte-unchanged; `drawToasts()` untouched (no banner-display gating — the
defect was in the award path, not the display); no registry rows.

## P7 — One powerup per dock visit; two DELIVERY score knobs

The four `deliveryCount` latches (8/12/16/20) collapse to one: `=== 8` kept, `=== 12`/`16`/`20`
deleted — the counter always passes through 8, so the equality already **is** the ">= 8, once per
visit" rule. Hauls of 7 or fewer still award nothing; `=== 12` Heavy Hauler and `=== CARGO_CAP_MAX`
Maxed Out/`superMegaDelivery()` are untouched (different mechanisms sharing numbers).
`DOCK_BASE_SCORE`/`DOCK_BONUS_STEP` promoted to `dockBaseScore`/`dockBonusStep` registry knobs
(DELIVERY, the `scoopHitsPerLevel` precedent), at their shipped values (50/25, unchanged this
changeset) — no score compensation (S4): the curve already pays `50 + 25×(n−1)` per piece, so a
24-piece haul (8,100) is already 6.75× a piece-at-a-time delivery, and the greed-vs-risk incentive
was already carried by the curve. Registry 111 → 113.

## ✅ GATE B — Playtest gate, closed 2026-08-19: every tunable answer "no change"

Zero knob moves, zero deferrals — every one of the eight live questions (item A's two were struck,
no caps having shipped) came back either "working as specified" or "no change wanted." The dock nerf
did not make big hauls unattractive (score alone still carries them); `dockBaseScore`/`dockBonusStep`
stay at 50/25. A single unshielded hit dumping the whole tow reads as fair, not punishing; the ship
shield feels *more* valuable with no tuning wanted, and — under play, not just argument — this
confirms FORK-CS037-B1 → no: the chain guard is unchanged in value because a hull hit dumps the tow
whether or not the guard is up. "Payload lost." fires only on genuine total loss. The two changes
together (C+F) balanced at 5/10 — they don't push late-wave play toward small hauls. The resume fix
produced 0 spurious banners, and a genuinely post-load-earned achievement survived into a fresh run.

**The gate's one actionable output was a defect, not a tunable:** on a hull hit, the ship re-hooks
its own released load almost immediately. Four compounding causes — a random release vector, a load
starting inside the pickup circle, knockback aimed at the hazard rather than the chain, and a Magnet
dragging the whole load straight back — none of them "the pieces are just nearby." This became P7.1.

## P7.1 — Tow release separation

Two mechanisms, both hooked only inside `damageShip()`'s existing `if (game.chain.length) {
scatterChain(); ... }` chain-loss block: every node `scatterChain()` frees is propelled radially away
from the ship at `DEBUG.towReleaseSpeed` (velocity **set**, never added — the CS035 P2 dock-lockout
push idiom, via a snapshot of `game.garbage.length` taken before the call and a loop over everything
appended past it), and `game.towLockoutT` arms to `DEBUG.towReleaseLockout` at the same instant.
While it counts down, the capture gate's hook `if` and `pulling` (never the raw `magnet` the two
budget-spend sites read — CS025 P1's split extended, not relaxed) both gate on `game.towLockoutT <=
0`. **Not** gated on `s.invuln` — the auto-shield save sets that too but keeps the cargo and arms no
lockout. `scatterChain()`/`Garbage.fromNode()` stay byte-unchanged; `breakChain()` keeps its old
random-scatter sever path untouched; `killShip()` gets neither mechanism. Two new SHIP knobs,
`towReleaseLockout` (`def` `HIT_STUN_DURATION`, 1.0 s) and `towReleaseSpeed` (`def` 120 px/s).
Registry 113 → 115.
